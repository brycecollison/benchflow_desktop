# Security checklist — Benchflow desktop

One page. Each row says what enforces it: a named test you can run, or a manual check written so
someone else can repeat it. Nothing here depends on trusting the developer.

How to run the named tests:

```powershell
venv\Scripts\python.exe -m pytest backend/tests -q        # offline checks, no real notebook
venv\Scripts\python.exe packaging\test_frozen.py          # drives the real Benchflow.exe
```

| # | Claim | How it is enforced |
|---|---|---|
| 1 | **The notebook stays on this machine.** SQLite, uploads and logs live in `%LOCALAPPDATA%\Benchflow`. The only things that ever leave are folders *you* chose: the backup folder and the SharePoint export folder. There is no cloud sync, telemetry or account in the build. | `packaging/test_frozen.py::test_bundle_holds_no_cloud_sdk_and_no_writable_state` fails if a cloud SDK (`boto3`, `botocore`, `aws*`, `azure*`, `msal`, `google*`, `dropbox`, `boxsdk`) ends up in the shipped bundle. Human: start the app, open Resource Monitor → Network, look for anything from `Benchflow.exe` that is not `127.0.0.1`. |
| 2 | **The API is reachable from this machine only, and a web page on another site cannot make it write.** uvicorn binds `127.0.0.1`, there is no CORS (`allow_origins=["*"]` from the web app is gone), and every write is refused when the browser's `Origin` is not our own — this app has no CSRF token, so Origin *is* the guard. | `backend/tests/test_api_safety.py` — cross-origin writes must be 403 (`http://evil.example`, `https://lab.example.com:8443`, and the look-alike `http://127.0.0.1.evil.example`), same-origin and script writes must go through, no `Access-Control-Allow-Origin` header anywhere. `backend/tests/test_desktop_cli.py::test_the_window_keeps_its_profile_and_binds_only_to_loopback` — `127.0.0.1` in `backend/desktop.py`, no `0.0.0.0` in `start-dev.ps1`. Human: from a second machine try `http://<this-ip>:8000/api/health` — it must refuse the connection. |
| 3 | **MCP is read-only.** `Benchflow.exe --mcp` gives an agent projects, experiments, sections, tables, attachment metadata and scientific metadata. It cannot create, edit, complete, delete, import, upload or run anything. | `backend/tests/test_parity_with_web.py::test_mcp_serves_the_same_tools_as_the_web_app` — the tool/resource names must match the web app's `mcp_server.py`, every `@server.tool` must declare `READ_ONLY` annotations, and `app/notebook_queries.py` must open the notebook with `?mode=ro` **and** `PRAGMA query_only=ON` (enforced by SQLite, not by politeness). `packaging/test_frozen.py::test_frozen_build_serves_mcp_over_stdio` — the shipped `.exe` answers `tools/list` and calls a tool over stdio. |
| 4 | **Nothing writable lives in the install directory.** The installer is per-user (`PrivilegesRequired=lowest`, no admin, into `%LOCALAPPDATA%\Programs\Benchflow`), and the notebook, uploads, logs, instance lock and WebView2 profile are in `%LOCALAPPDATA%\Benchflow` — never beside the exe. | `packaging/test_frozen.py::test_bundle_holds_no_cloud_sdk_and_no_writable_state` fails if `benchflow.db`, `lab_state.json`, `data/`, `uploads/`, `logs/` or a WebView2 folder appears next to `Benchflow.exe`. Human: install from a standard account with no admin prompt, save an experiment, close the window — no "access denied", and `%LOCALAPPDATA%\Benchflow\history` gains a snapshot. |
| 5 | **Uninstall keeps the data; a reinstall finds it.** `packaging/setup.iss` removes the program and never touches `%LOCALAPPDATA%\Benchflow`. | Human: uninstall from Windows, confirm `%LOCALAPPDATA%\Benchflow\benchflow.db` is still there, reinstall, open the app — the notebook you had is the notebook you get back. Deleting data on purpose is the researcher's own "delete everything" step, not the installer's. |
| 6 | **A backup or restore cannot be pointed at anything arbitrary**, and a network share is refused (a synced folder is a moving target mid-copy). | `backend/tests/test_desktop_cli.py::test_the_source_of_an_import_is_a_local_folder_and_a_network_share_is_refused`, plus `backend/tests/test_backup_schedule.py` and the folder picker tests (`backend/tests/test_folder_picker.py`) for the dialogs' validation. Human: in Settings → Backups, paste `\\server\share` and try to save — the Save button stays disabled. |
| 7 | **Closing the window finishes its work before the process dies** — backup and pending export first, then exit. A killed process is logged as such rather than pretending it finished. | `packaging/test_frozen.py::test_frozen_build_end_to_end` — configure a backup folder, send `WM_CLOSE`, assert a new snapshot landed in `<backup>\history` and the instance lock is gone. Human: Task Manager → end task while a backup runs → the log says the run was cut short, and the previous snapshot is still intact. |
| 8 | **No credentials in the app.** There is no account, no token file, no secret in the bundle; SharePoint export hands the file to a folder you already sync with the Microsoft account signed in to the machine. | Checked once by reading the source: the only match for `secret`/`token`/`password` in `backend/app/` is the stdlib `secrets` module used to make random upload names. Human (re-check after any upstream merge): `findstr /s /i "api_key password token bearer" backend\app\*.py`. |
| 9 | **Logs can name your files.** `backend.log` records start/shutdown, backups, and one line per MCP call (`[mcp] reading <path>`). Nothing scientific is quoted, but the notebook's paths are in there. | Human, before sharing the log with anyone: open `%LOCALAPPDATA%\Benchflow\logs\backend.log` (the Help & troubleshooting page collects it for you) and read it. It is in your own profile folder, so the ACL is your account's. |
| 10 | **Vendored code still carries one machine-specific path.** `app/onenote_importer.py` defaults `PALMISANO_LAB_BACKUP_DIR` to a `C:\Users\bryce\...` OneNote folder; `app/paths.py` has a dev-only `WEB_APP_SOURCE` fallback for the seed, unused in the frozen build. Neither runs unless you ask for that import. | Reported upstream (UPSTREAM.md). Human: Settings → Import from OneNote on a machine without that folder — it must say the folder is missing, not crash. |
| 11 | **The WebView2 profile holds preferences, never the notebook** (sidebar width, calendar tray, snap-to-grid, cookies, cache), in `%LOCALAPPDATA%\Benchflow\webview`. Deleting it resets the interface, not the science. | `test_the_window_keeps_its_profile_and_binds_only_to_loopback` keeps `private_mode=False` (WebView2's InPrivate mode keeps localStorage in memory, so preferences would vanish every restart). Human: change the sidebar width, restart the app, confirm it is still what you set. |
